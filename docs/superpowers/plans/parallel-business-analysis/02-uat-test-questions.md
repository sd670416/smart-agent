# UAT完整人工测试问题清单

日期2026-11-20。范围：文档第六部分已确认的场景1、2、3、4、6、7、8，以及跨场景、数据权限与异常情况。本清单尚未执行，不代表验收通过。

## 测试准备

1. 使用当前UAT配置启动最新smart-boot及smart-agent；前端本批无需更新。
2. 选三个真实可见项目，用它们的准确编号替换下文A、B、C；至少一个有合同和目标成本，一个有产值/回款，一个仍在建。另选一个缺预算项目用于验证数据缺失。
3. 选一个真实甲方名称、一个材料供应商名称，以及实际有采购合同的材料名称/规格。没有该类数据时测试结果允许为空，不代表功能失败。
4. 每组从新会话开始；组内连续追问在同一会话发送，验证上下文。测试跨场景切换时按专门顺序发送。
5. 准备一个有完整来源权限账号、一个缺部分来源权限账号。权限关闭场景只在既有测试配置允许时验证，不要求为测试改数据库或放开其他用户权限。
6. 展开AI处理信息核对实际工具和参数，但回复业务正文不应显示工具名、SQL、数据库字段或技术ID。

通用通过标准：每个事实追问重新调用工具；金额与审批完成业务记录对得上；合计来自全量范围；缺数据/权限说明原因，不补0；表格可读，名称中文，元/万元和百分比单位明确。

## 一 项目合同额排序

同一会话顺序发送。

| 编号 | 可以直接发送的问题 | 预期核对 |
| --- | --- | --- |
| P1 | 查询项目信息，按合同额从高到低排列 | 项目查询，取关联有效施工合同最终金额；普通项目审批完成且排除既定状态 |
| P2 | 改成从低到高 | 沿用项目范围，实时重查并升序 |
| P3 | 只看合同额超过300万元的项目 | 使用最终合同金额筛选，不换成项目预算 |
| P4 | 看第一条项目的档案 | 按本轮列表真实项目ID重新查询档案，不能跳到待办 |

同项目重复有效施工合同不能任意挑一条或合并成合法一对一；无合同金额不能伪造为0。原工具是否支持额外条件，以实际字段目录为准。

## 二 产值与付款分析 B

同一会话顺序发送，A替换为真实编号。

| 编号 | 问题 | 预期核对 |
| --- | --- | --- |
| V1 | 查询A项目实际完成产值、上报甲方产值和甲方累计回款 | 调projectOperation.query；完成/上报/确认按同一本期合计，不用清单应上报值 |
| V2 | 合同回款比例和产值回款比例分别多少？ | 继承A重查；分别除最终合同额和确认产值，其他收入不进分子 |
| V3 | 还差多少没有收回？其他收入有多少？ | 未收余额=确认产值−甲方回款，其他收入单列；负余额保留 |

| V5 | 汇总所有可见项目的产值和回款 | 清除单项目条件，全量汇总后重算比例，不相加一页数据或平均各项目率 |

数值例子仅用于核对公式：合同1000万元、产值250万元、甲方回款100万元，合同回款比例10%，产值回款比例40%，未收150万元。另有其他收入不改变这两种比例。

## 三 合作历史 C

先甲方组，供应商组另起会话。

| 编号 | 问题 | 预期核对 |
| --- | --- | --- |
| H1 | 查询某甲方的合作历史和累计回款 | 将“某甲方”替换准确名称；按真实甲方/合同关联，只含可见项目 |
| H2 | 只看2026年签约的合同 | 签约日期选择合同，显示这些合同当前累计账款，不把它解释成2026年资金发生额 |
| H3 | 合计合作过多少项目、合同额和未收余额多少？ | 项目按ID去重，合计全量，回款不含其他收入 |
| H4 | 看第一份合同的回款明细和开票申请明细 | 以真实contractId分别查询，开票为审批完成申请金额，不声称已打开完整表单 |
| H5 | 查询某供应商的材料合同合作历史 | 替换准确供应商；只选材料类型，不误要求其他三类合同 |
| H6 | 看第一份合同的结算明细 | 继承供应商/项目/真实合同，检查独立结算来源权限 |
| H7 | 再看这份合同的付款明细和收票明细 | 分别实时查询，付款与收票来源权限独立 |
| H8 | 汇总这个供应商所有材料合同的未付金额和票据覆盖率 | 全量净额，材料退款只调整一次，不能用分页原额明细代替净额合计 |

有同名合作方时应先确认编号；甲方/供应商类型不明确应先确认类型。若没有结算/收票等来源记录，区分真实无记录、无权限和金额缺失，不能一律按0解释。

## 六 经营横向比较 E

同一会话顺序发送。

| 编号 | 问题 | 预期核对 |
| --- | --- | --- |
| E1 | 比较A和B项目的合同额、目标成本、预算利润率、甲方回款和工期 | projectOperation.compare，2项目矩阵；默认A基准并说明 |
| E2 | 再加C项目，以B为基准 | 完整3项目重查，项目顺序保留，基准B真实ID |
| E3 | 只比较预算利润金额和预算利润率 | 保留项目与基准；金额差按各项目减B，率差单位百分点 |
| E4 | 去掉A项目 | 剩余B、C，B仍基准，不保留A数据 |
| E5 | 去掉B项目 | 只剩C不足2个，应要求补充项目；不能生成单项目假比较 |

基准删除追加测试：重新比较A、B、C，以A为基准，再说“去掉A”。仍有2项目但原基准已删除，应先确认新基准，不能暗自换成B。

同名追加测试：选择一个实际存在同名的项目与A比较，选择候选后只替换该位置，不能把整组覆盖成单项目。

数值公式：A利润率20%，B利润率30%，以A为基准时B差额为+10个百分点，不是增长10%或50%。缺预算/无权限格显示原因，差额空；未完工显示已施工天数，不给最终实际总工期。

## 八 经营风险及工期 F G H

每个风险维度可另起会话；涉及“这个项目/依据/只看”则留同一会话。

| 编号 | 问题 | 预期核对 |
| --- | --- | --- |
| R1 | 当前所有可见项目有哪些经营风险？ | 默认八维，不按当前页判断全部；风险和未评估项同时保留 |
| R2 | 只看高风险 | level=HIGH，重新查询；风险项目数去重，不宣称未评估规则已正常 |
| R3 | 汇总所有可见项目的风险数量和风险项目数 | summary全量汇总，区分项目数与提示条数 |
| R4 | 哪些项目有成本风险？ | COST，按一级科目：预算100万，净支出105/95/80万分别高/中/低；无预算未评估 |
| R5 | 哪些项目有付款风险？ | PAYMENT，结算净额100万、未付50/30/20万分别高/中/低；无结算不换合同额为分母 |
| R6 | A项目为什么有回款风险？ | RECEIVABLE，回款不含其他收入；低回款高风险还需工期过半，缺到期节点的长期规则未评估 |
| R7 | 查看A项目的开票风险及判断依据 | INVOICE，审批完成开票申请与回款差额，不称实际发票已开具或税损 |
| R8 | 查看A项目收票风险的金额和来源单据 | SUPPLIER_INVOICE，净额不重复减退款，不用别的合同多收票覆盖缺口，不认定税务违规 |
| R9 | 哪些项目进度延期？ | PROGRESS，仅有效计划/反馈事实；无反馈不简单当0，逾期任务有依据 |
| R10 | 哪些项目有质量风险？看一个项目的原因和依据 | QUALITY，问题子项闭环和期限；缺检查只是管理记录缺口，不认定质量事故 |
| R11 | 哪些项目有安全问题未关闭？ | SAFETY，检查/整改权限独立；不从自由文本猜重大隐患，缺检查不认定安全事故 |
| R12 | A项目合同工期多少，已经施工多少天，是否完工？ | siteFacts；合同工期、已历天数、完工依据分开；未完工不给最终工期；停工不套在建检查频次 |

风险数据不存在时不要求必须出现命中。人工核对来源日期、审批、净额、阈值及状态。系统当前没有可靠到期节点时，不能声称已完成超过90天无回款规则评估；普通风险金额不计审批中或未通过单据。

## 九 通用回归与权限

| 编号 | 操作或问题 | 预期核对 |
| --- | --- | --- |
| X1 | 同一会话：查项目信息→A项目产值回款→做盈利排名→查我的待办→查某供应商合作历史 | 各域正确切换，旧筛选不锁定新域 |
| X2 | 产值/比较/排名/风险各问一次“只看去年/按去年排名/去年对比” | 不支持的期间/历史明确说明，不能用去年创建项目代替去年利润或拿今天风险还原历史 |
| X3 | 使用缺财务或现场来源菜单账号重问 | 按对应业务说明无权或未评估；不能泄漏金额/证据，不把收票无权限说成项目无权限 |
| X4 | 使用只具预算来源权限账号问预算利润率排名 | 不要求不相关实际收支来源菜单；不可查的业务仍受限 |
| X5 | 由你调整测试账号的可见项目范围后，在旧会话继续查询 | 每轮重新取可信范围，不能因历史看到过就继续返回越权数据 |
| X6 | 提问一个不存在的项目/合作方，或实际同名项目/合作方 | 不存在说明原因，同名先确认；不能随意选择第一条或扩大成模糊查询 |
| X7 | 找一条业务新增/更新并审批完成后，在同会话说“重新查一下” | 工具重新调用，反映最新有权数据；审批中、未通过不得进入业务金额 |
| X8 | 检查正文及AI处理信息 | Markdown正常；正文中文业务列，排序/基准/单位明确；技术工具名、ID、SQL只在AI处理信息出现 |

金额=0、无记录、金额空值、无权限、尚不支持是不同情况。尤其不能把无预算、缺产值、无可靠日期、无检查权限统一解释为0或无风险。

## 如何记录失败

每个失败保留：测试编号、账号、原问题及紧邻的上一轮、预期/实际、截图和本轮conversationId/runId/traceId。优先复制AI处理信息中的实际工具参数与错误；不要只截最终“查询失败”。同一问题修改后换新runId复测。

验收记录可按以下字段追加：`编号 | 待测试/通过/不通过/无对应数据 | runId | 差异说明`。本文件尚无人工通过记录。

推荐先做V1/V2、H1/H5、E1、D1、R1/R12，再测各组追问，最后权限和异常。核心通过后再扩展更多项目样本，不用一开始逐页核对全库。
