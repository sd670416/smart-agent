## 本批范围

- 新增付款申请独立业务域及查询工具，查询结果回交模型组织业务答复；每轮事实查询重新调用接口。
- 支持申请单列表、付款明细、申请单数、明细条数及本次付款金额合计。
- 支持项目定位、申请单号、申请单ID、申请创建日期及项目创建日期；日期含义不明确时追问，不猜测。
- 支持“第一单”等当前列表引用；历史数据仅用于定位申请单，明细与金额重新查询。
- 不包含其他付款申请、项目报销、退货退款、实际总付款及垫资利润。2026-10-21追加同比、环比与两组比较，详见[比较实施与验收](2026-10-21-payment-request-comparison.md)，待人工验收。

## 数据与权限

| 内容 | 实现口径 |
| --- | --- |
| 权限 | 财务付款申请叶子菜单 `/finance/bus-finance-payment-request`，可信权限 `menu:finance:payment-request`；system账号直接授权 |
| 数据范围 | 接口校验可信签名上下文、租户、可见项目；不接受模型扩大范围 |
| 状态 | 申请及项目均审批完成；排除已删除记录及项目状态1/3/10 |
| 本次付款金额 | 子表 `current_payment_value` 累计，不使用主单或明细累计付款字段替代 |
| 列表分页 | 明细先按申请单及租户汇总，再分页主单；汇总不累加单页数据 |
| 明细 | 合同名称、合同类型、供应商名称、付款类型、本次付款金额、累计结算/收票/付款金额 |
| 名称关联 | 合同类型、项目与租户一致且合同审批完成；无有效名称显示“未维护或不可用” |
| 日期 | `createDate`为申请创建日期，`projectCreateDate`为项目创建日期；结束日包含全天 |
| 金额缺失 | 明细本次金额缺失或主单无明细时拒绝形成不完整合计；无匹配申请则返回零 |
| 敏感信息 | 不返回银行、银行卡号、账户及附件信息 |

内部链路：`paymentRequest.query` → `/internal/ai/tools/payment-request-query` → 付款申请查询服务。付款类型采用原字典父子结构解释；业务答复使用中文列名。

## 验收方法

需要重启 **smart-boot、smart-agent**；smart-web无变更。未启动本地服务、未连接业务数据库、无需数据库结构变更。

| 操作/问法 | 预期 |
| --- | --- |
| 查询付款申请列表 | 仅返回授权项目下审批完成申请，中文列名 |
| 接着问“合计多少” | 重新查询全量单数、明细条数、本次付款金额，不累计当前页 |
| 接着问“看第一单付款明细” | 定位上一列表首单并重新查询；显示合同及供应商名称 |
| 按申请创建日期查询2026年9月付款申请金额 | 按申请创建日期统计，包含9月30日全天 |
| 本月付款申请 | 对未明确的日期维度追问，选择后再查 |
| 查询某项目的付款申请 | 项目同名时确认，不能扩大当前可见项目范围 |
| 付款申请待办 | 使用审批查询，不将业务查询冒充待办 |
| 无付款申请菜单账号查询 | 返回针对付款申请的友好无权提示，不返回项目无权的错误说法 |

人工对账：原付款申请页面选择相同审批状态、项目和日期；核对主单条数、子单明细及本次付款金额。付款申请不等于已实际支付总额。
