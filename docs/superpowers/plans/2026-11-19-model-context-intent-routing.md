# 模型上下文意图路由改造

目标：每轮由模型结合上下文判断业务域和动作；无法确定时先追问，不以关键词或“继续=下一页”固定规则替代理解。

已确认设计：同一运行复用当前模型和权限上下文。模型只提出意图，程序校验能力注册、权限和参数，业务工具与后端仍负责权限、范围及实时查询。

## 任务

- [x] 新增模型意图判定器，从业务域与工具注册表动态生成能力清单，使用独立指令及结构化判定协议。
- [x] 提供近期对话、当前业务域、查询条件、分页/结果引用摘要、当前页面及待确认事项；控制大小，历史数据只用于理解。
- [x] 接入生产会话链路，绕过关键词路由与固定翻页/序号自动执行；保留用户明确点击确认及后端校验。
- [x] 明确执行、追问、普通回应的处理；判定失败不回落关键词或历史业务；保存追问以支持后续回答。
- [x] 在 AI 处理信息中记录意图模型请求、判定结果及失败情况，业务回复不暴露技术字段。
- [x] 编译验证并提供用户验收步骤；按用户要求不启动应用、不执行完整测试。

状态：开发和编译完成，业务待用户在 uat 环境验收。

## 边界

- 不增加依赖，不修改数据库结构，不切换用户分支，不修改 uat 数据。
- 生产默认使用模型判定；旧构造保留供现有测试和兼容场景使用。
- 新业务通过现有 BusinessDomainContributor 和 AgentTool 注册表扩展，不新增业务关键词分支。
- 对模型输出进行协议、已注册业务及权限校验，不允许路由模型直接执行业务工具或生成查询结果。
- 查询参数由后续业务模型按工具 schema 生成并由 ToolExecutor/后端校验；继续查询仍实时调用工具。
- 外部模型故障、超时沿用失败反馈，不将基础设施故障伪装成用户意图歧义。

## 实现与验证

- ModelIntentRouter 仅提供 routing.decide 作为结构化意图提交协议，不注册为业务执行工具；运行复用当前绑定模型。
- kind 为 QUERY、CLARIFY、RESPOND、UNSUPPORTED，动作由模型用自然语言理解，程序没有“继续=下一页”的映射。
- 有效协议但不能校验的业务域或输出结构转为追问；模型服务超时或失败按原有错误反馈，不静默转其他业务。
- 查询参数继续通过原业务工具 schema 生成并在 ToolExecutor 和后端校验；业务执行再次核对工具所属域。
- 模型路由判定保存到现有 ai_conversation_context 的 MODEL_ROUTING_INTENT，不新增表；追问可在后续会话继续理解。
- 同时修正材料价格工具 schema 中当前网关不支持的 enum/minimum/maximum 声明，取值范围仍由输入对象和后端严格校验。
- 验证：smart-agent 的 Maven 离线 test-compile（跳过测试执行）通过；smart-web 的 pnpm build:test 通过，存在既有打包体积及混合导入警告。
- 未调用线上模型做验收，未启动服务，未执行自动化测试，未修改数据库结构或业务数据。

## 用户验收

更新并重启 smart-agent，更新 smart-web；smart-boot 无需因本次改造重启。

1. 原审批会话中发送“查询一下安全服的历史价格”：应由意图模型切换材料价格查询，实际调用 materialPrice.query。
2. 返回有下一页的材料列表后说“继续”：结合上一轮回答与分页状态判断操作；语义唯一时重新调用同一业务工具并保留筛选，不应无条件追问或固定翻页。
3. 上一轮给出多个后续操作后说“下一步”：应追问确认，而不是猜测。
4. 空白会话仅发送“继续”：应询问要继续什么，不自动查询项目或待办。
5. 项目列表后追问“审批完成的有多少”：保持项目业务并按支持状态实时查询；明确说“改查我的待办”才切换审批。
6. 对追问直接回复业务选项：应结合原问题执行；已存在的确认按钮仍按用户明确选择处理。
7. 刷新历史会话：AI处理信息仍应显示“理解上下文”“意图判定”，可展开原始判定记录；业务正文不出现内部编码。
8. 无权限账号查询明确业务：返回对应业务权限提示，不改用其他来源绕过。

下一步：用户验收本改造的路由切换、连续追问和实时查询，再根据实际失败会话调整能力描述或上下文摘要。
