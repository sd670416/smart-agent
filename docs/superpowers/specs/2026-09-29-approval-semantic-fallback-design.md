# 审批查询不支持条件时的二次筛选设计

## 范围

首阶段只处理 `approval.query` 的待办、已办、我发起查询。`smart-boot/dev2` 负责身份校验、权限过滤和候选数据读取；`agent/dev` 负责意图区分、模型语义筛选、结果校验、计数与分页。现有直接支持的字段继续走原查询逻辑。`smart-web/dev2` 现有聊天和工具结果展示能够复用时不改动。

## 查询决策

1. 模型把用户问题解析成查询范围、条件、排序和分页请求。`agent` 先按字段目录判断条件是否被当前业务查询支持；不能把“接口不支持字段”与“意图解析错误”混为一谈。例如“3 天没处理的待办”应使用任务创建时间进行精确筛选，不能误判为发起部门。
2. 全部条件受支持时，调用现有 `approval.query`，保持当前权限、筛选、排序、聚合和分页行为。
3. 仅有不支持的条件时，先调用 `smart-boot` 的候选查询能力。该能力在原审批查询权限逻辑内确定可见范围，返回权限过滤后的候选记录；不接受模型提供的用户 ID 或权限范围作为可信依据。
4. 对候选记录中的时间、数值、布尔等可确定条件，由程序筛选。需要理解名称、备注、表单文本等语义条件时，模型按批次筛选。模型只能返回候选记录 ID、匹配与否及简短依据；`agent` 校验返回 ID 属于当前批次，拒绝额外 ID、重复 ID 和格式错误结果。
5. 所有候选批次处理完毕后，由程序计算匹配总数、排序和分页，再将该页结果交给正常回答链路。模型筛选期间不能先对候选集分页，不能把部分处理结果报告为完整统计。

## 不完整与不确定

- 候选查询必须有可验证的完整性标记和总数。若超过既有 10000 条上限、来源分页不完整、超时或模型批次失败，则不返回伪完整结果；要求用户缩小范围。
- 若候选数据没有判断某条件所需的信息，模型不得猜测。系统列出不可判断条件和可用字段，供用户改写或选择。
- 语义筛选的无法确定项单独计数，不纳入确定匹配总数；回答中说明筛选是基于已返回内容的语义判断，不将其表述成数据库精确统计。
- 每轮重新读取权限过滤后的当前数据，不把历史查询结果当作候选数据。会话上下文只帮助理解意图。

## 接口与安全

- 候选查询接口与现有内部审批接口使用相同的签名、身份上下文和权限策略，不新增绕过权限的路径。
- 返回给模型的字段采用最小必要投影，不传无关个人资料、密钥或完整附件。模型输入记录 ID 与字段值，模型输出结构化结果。
- 审计记录原查询条件、候选数量、筛选方式、处理批次、最终数量及失败原因；不记录完整敏感表单文本。

## 验收

1. 受支持字段查询的结果与原行为一致。
2. 不受支持但候选数据包含判断依据的语义条件，可以在权限范围内完成全量筛选，最后分页；第二页与总数一致。
3. 接口权限范围以外的记录无法通过模型输出注入结果。
4. 数据不足、超过上限、模型输出无效或仅处理部分批次时，不显示完整结果或错误总数。
5. “3 天没处理的待办”走任务创建时间的确定性筛选，而非语义兜底；“发起部门”与“所属部门”不会自动等同。

## 用户验证

由用户在目标分支自行编译并测试：分别启动更新后的 `smart-boot` 和 `agent`；若 `smart-web` 未改动则不需重建前端。用同一账号对比普通待办查询、3 天未处理、语义条件、无依据条件和多页结果，并对照原页面的权限范围。
